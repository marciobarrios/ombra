# Ombra agent notes

Ombra is a shadcn registry, not an npm component library. Users copy files. Do not add a runtime dependency to the core beyond React, `@base-ui/react`, and `cn`.

## Linear issues and pull requests

- Confirm that each Linear issue belongs to Ombra and matches the change before linking it.
- For every issue fully resolved by a PR, include a separate `Fixes MAR-123` line in the PR description, replacing the example with the actual issue identifier. A bare ID, branch name, or PR comment is not a substitute for an explicit closing keyword in the description.
- For partial work, investigations with remaining acceptance criteria, or related follow-ups, use `Refs MAR-123` (contributing work) or `Relates to MAR-123` (context only). Gate issues are the exception: see Real-iPhone verification. Do not use a closing keyword until the PR completes the issue's scope.
- Before handing off a PR, verify its saved description contains the intended closing lines and the issues are linked in Linear. Automatic completion requires the team's GitHub integration to map **On PR or commit merge** to **Done**; when multiple PRs implement one issue, completion waits for the final linked PR. See [Linear's GitHub integration docs](https://linear.app/docs/github).
- When reconciling stale issues, verify the implementing PRs have merged and the issue's acceptance criteria are satisfied, then mark the issue Done with links to the merged PRs. Keep issues open when implementation or required validation remains.

## Real-iPhone verification

- Feature issues must not wait on a physical iPhone. Accept them on automated evidence: the Playwright projects and, where useful, the iOS Simulator.
- Each milestone has one gate issue that collects every device-only check (feel, frame time, VoiceOver, Low Power Mode), run in one session near the end of the milestone: Spike is MAR-12, v0.1 MVP is MAR-81, v1 is MAR-82.
- When an issue has a check only a real device can judge, add it to its milestone's gate checklist and relate the two issues. Do not add "confirm on a real iPhone" to the feature issue's acceptance criteria.
- Keep a real-device check in a feature issue only when the issue cannot be judged at all without it, and say why in the issue.
- A failed gate check gets its own bug issue, linked from the gate.
- Never mention a gate issue in a PR description or commit message, not even with `Refs` or `Relates to`. Linear's GitHub integration moves any issue a new PR mentions to In Progress, and a gate must stay in Backlog until its session runs. Note the PR in a comment on the gate instead.

## Simulators and emulators

- When you finish testing on an iOS Simulator or Android Emulator, release it before your final reply: close every device you opened (in T3 Code, `device_close`). An open device keeps its claim, and other threads get `DEVICE_IN_USE` until it is released.
- Release only devices you opened. Never close another thread's session unless the user asks.
- Also stop any dev server you started for device testing.

## Stack

- pnpm 10, Node.js 24 (`.nvmrc`). This VM’s `/exec-daemon/node` is Node 22 and sits earlier on `PATH`. Put the Node 24 bin first before `pnpm`, `next`, `oxlint`, or Playwright.
- React 19 and Next.js 16 (App Router, Cache Components) in `apps/docs`.
- TypeScript 7. Next 16.4 typechecks with the project-local `tsc` CLI. Leave that default alone (`useTypeScriptCli` stays on). TypeScript 7.0 has no programmatic API. `pnpm typecheck` runs `next typegen` first because `next-env.d.ts` and the route types are generated and gitignored.
- Tailwind CSS 4. Registry files are scanned with `@source "../../../registry"` in `apps/docs/app/globals.css`.
- shadcn on Base UI (`components.json` style `base-nova`). `lib/utils.ts` re-exports the `cn` package. Dialog primitives come from `@base-ui/react/dialog`.
- Oxlint and Oxfmt. The anti-slop plugin is vendored at `tools/oxlint/anti-slop` (ignored by both tools). `@oxlint/plugins` must match the installed `oxlint` version exactly. Record any rule relaxation with an inline comment saying why.
- Playwright projects: `chromium`, `webkit`, `chromium-mobile` (Pixel 7), `webkit-mobile` (iPhone 13). WebKit here is not iOS Safari.
- Keep the Playwright suite small. It covers core behaviour only (open and close morph, navigation, pull to dismiss, zoom, focus and accessibility, the `OmbraRoot` contract, the registry files), and CI should finish it in a few minutes. Every browser test runs four times, once per project. CI runs each project in its own job; pull requests skip desktop `webkit`, which runs on every push to `main`. Do not add a spec per edge case, engine or spike experiment. Specs that need no browser run once, in the `unit` project (`unitSpecs` in `playwright.config.ts`).
- Add a browser test only for a crucial feature, and only what a unit spec cannot show. Put decision logic in a pure module and cover its cases in the `unit` project; the browser test then checks the one behaviour a user would notice. A feature gets at most one new browser test, added to the existing spec for its area, reusing that spec's helpers rather than adding new ones. Keep each test short: no step-by-step tours of every input, and no case that an existing test already covers. If a change needs more than that, say so in the PR instead of growing the suite.

## Registry

- Item names are `ombra-*`.
- Source lives in `registry/ombra`. `registry/package.json` exists only so the workspace can resolve `react` and `@base-ui/react` for files outside `apps/docs`. `shadcn build` does not publish that package file. Run the build from the repo root: `shadcn build registry.json -o apps/docs/public/r`. Paths in `registry.json` are relative to that file, and the CLI resolves them from the process cwd.
- Built JSON under `apps/docs/public/r` is generated. Do not commit it.
- Every registry file has `target: "components/ombra/<file>"`, because the files import each other relatively. A new file needs one too, and a relative import must point at a file in the same item (`e2e/registry-items.spec.ts` checks both).
- Global CSS the viewer needs ships through the item's `css` in `registry.json`, never only through the docs app's `globals.css`. The pull styles live in both; keep them the same.
- Registry code must typecheck in a consumer's project: TypeScript 5 or 6, no `@types/node` (Vite).
- The spike UI may live in `apps/docs/app/spike`. Promote something into `registry/ombra` only when the behaviour is worth keeping.

## State

- Never use `useState`, in the registry or the docs app. Oxlint enforces this with `no-restricted-imports`, which also bans the default `react` import so `React.useState` cannot slip through. Import hooks by name. There is no exception or disable comment. If the rule ever seems wrong, change it here first.
- Use `useReducer` with actions named after events (`open-requested`, `opened`, `pull-started`), not commands or setters (`open`, `set-index`). A new piece of state means a new action and a transition, not another loose flag.
- For an external source (matchMedia, a store), use `useSyncExternalStore`.
- The gallery's core state lives in `registry/ombra/gallery-state.ts` with no React import, so other variants can reuse the reducer (MAR-40). Keep DOM nodes and `Animation` objects out of it. DOM-derived state (decoded photos, strip overflow, the track node) stays in a local reducer in the component.
- `OmbraRoot` (`registry/ombra/ombra-root.tsx`) owns that reducer and identifies items by stable string IDs, never by index (MAR-138). It decides open and active-item state, controlled or not; the viewer is its driver, runs the morphs, and reports phases back. Ask through `requestOpen`, `requestClose` and `requestActive`, so a controlled parent can refuse. Indices stay only as positions in the viewer's DOM lists. The browser contract specs run on the `/spike/root` bench.
- `useReducer` does not bail out early: dispatching an action that changes nothing still re-runs the component. Before dispatching from a hot path (scroll, resize, pointer move), use `useReducerWithBailout` from `registry/ombra/use-reducer-with-bailout.ts`, which drops actions that change nothing. The reducer must return the same state object when nothing changes.
- Values that change every frame stay out of React state, in refs or CSS variables such as `--ombra-pull-live`.

## Spike behaviour

- Missing `?engine=` defaults to `flip`, matching the product default confirmed in MAR-12 on 6 November 2026. View Transitions remain optional. Reduced motion forces `fade`. The easing is the cubic `cubic-bezier(0.22, 1, 0.36, 1)`, decided in MAR-12 on 12 November 2026: the spring (`?spring=1`) felt no different on a real iPhone, so it stays a spike experiment and is not promoted to the registry.
- Morph engines: `vt` (View Transition API), `flip` (WAAPI FLIP on a fixed clone), `fade`. `resolveMorphEngine` in `registry/ombra/morph.ts` picks the one that runs: reduced motion fades, and `vt` without `document.startViewTransition` runs FLIP.
- Both engines put the photo on the same pixels at the same progress: FLIP moves the visible box in a straight line, as a view transition's group does, rather than interpolating the crop (MAR-15). A hand-off onto the real photo uses the same sampled keyframes (`flightKeyframes`).
- A view transition keeps one named group. `runViewTransition` sets `data-ombra-morph` on the root, and `MORPH_STYLES` clears every other `view-transition-name` while it is set. The shared element takes its name inline with `!important` (`nameSharedElement`). `OmbraPortal` renders `MORPH_STYLES` outside the dialog, so a closing transition still has it.
- A close during an opening leaves from the current frame and the scrim it reached. A VT opening hands its live box to a FLIP clone first, because a view transition cannot run backwards.
- The FLIP clone animates `transform` only, so the compositor runs it: WebKit runs a `clip-path` animation (and the `transform` in the same effect) on the main thread, which dropped frames in Low Power Mode (MAR-96). The crop is a clip box with `overflow: hidden` whose non-uniform scale sets the visible area, and the image inside counter-scales. The clip box's `border-radius` is counter-scaled on each axis so the corners stay 6px on screen, matching the photo and the thumbnail. It runs in an effect of its own, never in the effect with `transform`, so the transform effect stays on the compositor. The clone is on `document.body` so the dialog cannot clip it. A hand-off onto the real photo still uses `transform` and `clip-path`.
- Slide track and thumbnail strip use native scroll-snap. Zoom sets `overflow: hidden` and `touch-action: none` on the track until the scale returns to 1. A pan past the zoomed photo's edge sets `scrollLeft` from the finger with scroll snap off (mandatory snap would pull each small scroll back), holds the index, and on release glides to the chosen slide before snap returns (MAR-104). `registry/ombra/gesture-arbitration.ts` is the behaviour table (mode by input: track, zoom, pull or none) that `use-zoom.ts` and `use-pull.ts` follow (MAR-22). A pinch while the track has not come to rest on the active slide waits, and starts from the fingers' spread once it rests, so a zoom never starts between two slides. A pull, once locked, and an edge hand-off ignore a second finger. Change the table and its unit spec together.
- Zoom stops where the media shows at its natural size (the `width` given to `OmbraMedia` over its fitted width), never below 1, unless `OmbraZoom` has a `maxScale` hint (MAR-21). The ceiling math lives in `registry/ombra/zoom-limit.ts` with its unit spec. The ceiling and the layer box are measured on a press or a discrete zoom, never in a pointer move. The first zoom past 1 sets each `img[srcset]`'s `sizes` to the magnified width, so the browser fetches a sharper file.
- A track scroll during opening ends the clone: the rest of the FLIP animation continues on the real hero at the same `currentTime`, and the popup's fade moves to the parts around it so the photo stays opaque. VT lets touches through with `--ombra-vt-pointer-events` and restarts from the live group box, because a view transition cannot move onto an element. That only helps where the browser honours it: on a real iPhone (Safari) the swipe is still blocked until the VT opening ends, which MAR-70 accepted because VT is optional.
- Pull to dismiss works up or down, by touch, mouse drag, or trackpad swipe. `--ombra-pull-live` is signed (negative while the photo is pushed up). A trackpad swipe arrives as wheel events with no release, so it dismisses as soon as it crosses the threshold, settles back once the wheel goes quiet, and swallows the momentum that follows a dismissal so it cannot scroll the page. While the viewer is still closing, every event in the swipe's direction is swallowed: a close onto an off-screen thumbnail unlocks the page, a page scrolling under the flight sends it chasing the thumbnail, and real momentum is too noisy to tell from a new scroll (Chrome merges events when busy). Once the viewer is gone, only the decaying tail is swallowed: once the wheel speeds up, turns around, goes sideways, or holds steady (mouse notches), the person is scrolling again and every later event reaches the page. A swipe's momentum keeps the wheel busy, so a plainly vertical wheel event ends a sideways gesture and pulls even while the track still snaps, and a plainly sideways one ends a pull and goes to the track. A wheel stream that began outside the viewer (a page scroll still running when a click opens it) is ignored until it pauses. A gesture takes the photo over only once it turns out vertical, so a tap or a sideways swipe lets a snap-back finish, and the pull starts from the pose on screen, so momentum that arrives as a second burst during a snap-back does not jump the photo to the centre. A drag waits for nothing: while the track still snaps, only a plainly vertical one pulls, so a slightly diagonal flick to the next photo cannot close the viewer.
- A vertical drag or trackpad swipe during a FLIP or fade opening cuts it and closes from the clone's current pose. A VT opening already closes on that press as an outside press.
- A close with no box to land on fades: the trigger unmounted, or a scroll container still clips it after the reveal (`mostlyVisible` checks clipping ancestors, not only the viewport). Focus then goes to the nearest rendered trigger. Never morph to a different photo's thumbnail (MAR-16).
- A FLIP flight follows its target while it is in the air: `watchLayoutShift` reports viewport resizes and page scrolls outside the viewer, and the flight replays the remaining time towards the new box. The clone is removed only once the image under it has decoded (`whenDecoded`).
- The viewer focuses its close button itself with `preventScroll`. Base UI's default initial focus scrolled the page to the portal at the end of the document, so every close had to scroll back to its thumbnail.
- The docs site follows the system light or dark setting (`prefers-color-scheme`; Tailwind's `dark` variant is media-based until the MAR-106 toggle). The viewer's backdrop and chrome take the page's `background` and `foreground` tokens, never fixed black or white: iOS Safari picks its bar colour while the backdrop fades in, and any other backdrop colour leaves grey bars around the viewer (MAR-105).
- Pull progress is the CSS variable `--ombra-pull-live` on `documentElement`, not React state, so a drag does not re-render every frame. Consumer styles read the public runtime contract instead: `OmbraContent` and `OmbraBackdrop` publish `--ombra-pull` (an alias of the live value), `OmbraContent` publishes `--ombra-zoom` (the active photo's scale, 1 at rest, written by the zoom gesture), and the viewer reports state as `data-phase`, `data-pulling` and `data-zoomed`.
